# 03 - Controller Validation

This is the third stage of the Tool Orchestration project.

The planner can now create structured plans with dependencies and result references. This stage adds a controller-side validator so the system does not trust LLM output blindly.

No tools are executed in this stage.

## Goal

```text
User request
↓
LLM planner
↓
Structured plan
↓
Controller validation
↓
Valid plan → continue
Invalid plan → reject
```

The central idea is:

```text
LLM proposes
Controller verifies
```

A plan being valid JSON does not mean it is safe or executable.

## Planner

The planner still has the same responsibility as the previous stages:

```text
natural-language request
↓
structured workflow plan
```

Each step follows this shape:

```json
{
  "step_id": 0,
  "tool": "search_flights",
  "arguments": {},
  "depends_on": []
}
```

Arguments may also reference earlier step outputs:

```json
{
  "result_of": 0
}
```

The planner does not execute tools.

After parsing the LLM response, the generated plan is passed to the validator before it is accepted.

## Tool Schemas

The available tools define the names and expected argument structures.

Current tools:

```text
search_flights
search_hotels
calculate_cost
```

Example tool schema:

```python
search_flights = {
    "type": "function",
    "function": {
        "name": "search_flights",
        "parameters": {
            "from": "string",
            "to": "string",
            "date": {
                "day": "number",
                "month": "number",
                "year": "number"
            }
        }
    }
}
```

The validator uses these schemas instead of trusting argument names and types generated by the model.

## Validation Pipeline

```text
validate_plan(plan)
        ↓
validate_plan_structure
        ↓
validate_plan_step_ids
        ↓
validate_tool_args
        ↓
validate_steps_dependecny
        ↓
validate_result_dependency
```

A valid plan returns:

```python
True
```

An invalid plan raises a specific validator exception.

## Validation Rules

### 1. Plan structure

The validator checks that:

```text
plan is a non-empty list
each step is a dictionary
each step contains exactly:
    step_id
    tool
    arguments
    depends_on
tool exists
arguments is a dictionary
depends_on is a list
```

This prevents malformed planner output from reaching later stages.

### 2. Step IDs

Step IDs must be:

```text
integers
unique
sequential
in the same order as the plan
```

Example:

```text
0
1
2
3
```

A plan such as:

```text
0
2
1
```

is rejected.

This stage intentionally keeps step ordering strict and simple.

### 3. Tool arguments

Arguments are validated against the tool schema.

The validator checks:

```text
exact parameter names
nested object structure
string values
numeric values
null values
result_of references
```

For example:

```json
{
  "date": {
    "day": 25,
    "month": 10,
    "year": null
  }
}
```

is valid because `null` is allowed when the planner cannot safely infer a missing value.

A previous-step result may replace a literal value:

```json
{
  "hotel_cost": {
    "result_of": 2
  }
}
```

### 4. Dependencies

Each dependency must refer to an earlier step.

Example:

```json
{
  "step_id": 3,
  "depends_on": [0, 1, 2]
}
```

The current rule:

```text
dependency < current step_id
```

also prevents:

```text
self dependency
forward dependency
dependency cycles
```

Because plans are required to use sequential, ordered step IDs, explicit graph cycle detection is not required yet.

This is a deliberate simplification for this stage.

### 5. Result references

A `result_of` reference must:

```text
contain only result_of
contain a numeric step ID
reference an earlier step
reference a step declared in depends_on
```

Valid:

```json
{
  "hotel_cost": {
    "result_of": 2
  }
}
```

with:

```json
"depends_on": [0, 1, 2]
```

Invalid examples:

```json
{"result_of": "2"}
{"result_of": 99}
{"result_of": 3}
{"result_of": 2, "extra": true}
```

A reference is also invalid if step `2` is not present in `depends_on`.

This keeps execution ordering and data provenance consistent.

## Validation Errors

The validator uses explicit exception types:

```text
PlanValidatorException
├── PlanStructureError
├── PlanArgumentError
├── PlanDataError
└── PlanDependencyError
```

This is more useful than returning only `False`, because the controller can understand why a plan failed.

Examples:

```text
PlanStructureError
→ malformed plan or unknown tool

PlanArgumentError
→ wrong argument name or argument type

PlanDataError
→ invalid or out-of-order step IDs

PlanDependencyError
→ invalid dependency or result reference
```

These errors can later be used for debugging or re-planning.

## Important Learning

The main lesson from this stage is:

```text
structured output
≠
valid workflow
```

An LLM can produce JSON that looks correct while still containing:

```text
unknown tools
wrong parameters
duplicate IDs
invalid dependencies
missing result references
future references
undeclared data dependencies
```

The controller must validate these constraints before execution.

The architecture now looks like:

```text
User
↓
Planner LLM
↓
Structured Plan
↓
Validator
↓
Trusted Plan
```

## Current Limitations

This stage still does not:

```text
execute tools
track step state
detect ready steps
run independent steps
store tool results
resolve result_of values
retry failed tools
handle timeouts
re-plan
```

The validator also intentionally uses a strict ordered-step model, so general DAG cycle detection is not required yet.

## Next

Stage 04 introduces DAG execution.

The next question becomes:

```text
Given a validated plan,
which steps are ready to run right now?
```

Example:

```text
step 0 ──────┐
step 1 ──────┼──► step 3
step 2 ──────┘
```

Initially:

```text
READY → 0, 1, 2
WAITING → 3
```

After steps `0`, `1`, and `2` complete:

```text
READY → 3
```

That is where the project moves from planning and validation into actual workflow execution.
